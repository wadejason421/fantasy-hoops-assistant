# 04 — 推薦引擎：它憑什麼說你該撿誰

核心主張：**H2H 類別制的每日決策，不是「挑最強的球員」，是「把搖擺類別的勝率推過 50%」。**

## 一、為什麼不能用「球員排名」來做每日決策

一般的 fantasy 排名（Z-score、Hashtag 的總分、Yahoo 的 O-Rank）都是**靜態、無上下文**的。它們回答「這個球員整季平均而言多有價值」。

但你每天面對的問題是：**在這個特定對手、這個特定週、這些特定剩餘場次下，誰能多贏一類。**

這兩件事會給出不同答案。極端例子：

> 本週還剩 2 天。你 BLK 領先 6.0（穩贏）、PTS 落後 95（穩輸）、STL 落後 0.8（搖擺）。
> FA 上有 A（場均 22 分 1.2 阻攻 0.3 抄截，剩 2 場）和 B（場均 7 分 0.2 阻攻 1.9 抄截，剩 2 場）。
>
> 任何排名都說 A 遠優於 B。
> **正確答案是 B** —— A 的 44 分填不平 95 分的洞，1.2 阻攻投進一個你已經贏 6 個的類別；B 的 3.8 抄截直接把 0.8 的落後翻成 3.0 的領先，多贏一類。

這就是整個引擎要做的事。學術上這叫「draft/roster context 感知」—— Rosenof 的論文明確指出 Z-score 和 SGP "are both fundamentally limited because they do not account for drafting context"。

## 二、演算法：五個步驟

```
步驟 1  取本週狀態
        GET /league/{lk}/scoreboard;week={w}
        → 我方各類別累積 S_me[c]、對手各類別累積 S_opp[c]
        （一個請求就有，這是 Yahoo API 最值錢的端點）

步驟 2  取剩餘賽程
        ESPN scoreboard（今天到本週結束的每一天）
        → 每個球員本週還剩幾場 G[p]

步驟 3  投影剩餘期望值
        每個球員每場的類別期望 proj[p][c] 與場間標準差 sd[p][c]
        我方剩餘期望  E_me[c]  = Σ_p∈先發 G[p] × proj[p][c]
        對手剩餘期望  E_opp[c] = Σ_p∈對手先發 G[p] × proj[p][c]

步驟 4  算每個類別的勝率，分成三類
        diff[c] = (S_me[c] + E_me[c]) − (S_opp[c] + E_opp[c])
        var[c]  = Var_me[c] + Var_opp[c]
        P_win[c] = Φ( diff[c] / √var[c] )          ← TO 類別反向

        lock  : P_win ≥ 0.85   → 已鎖定，不再投資
        punt  : P_win ≤ 0.15   → 放棄，不再投資
        swing : 0.15 < P < 0.85 → 唯一的戰場

步驟 5  對 swing 類別排序候選球員
        value[p] = Σ_{c ∈ swing} w[c] × G[p] × proj[p][c] / σ_lg[c]

        w[c] = 邊際勾率斜率 = φ( diff[c]/√var[c] ) / √var[c]
               （標準常態的 pdf —— 越接近 50/50 的類別，每多一個單位
                 帶來的勝率提升越大，權重自然越高）
```

**步驟 5 的 `w[c]` 是整個設計的關鍵。**它用機率密度函數當權重，自動產生「鎖住領先、放棄落後、全力搶搖擺」的行為 —— 不是寫 if-else 規則硬編進去的，是數學推出來的。P_win 在 0.5 附近時 φ 最大，在 0.05 或 0.95 時 φ 幾乎為 0。

這也剛好符合社群共識（「串流用來確保拿下類別」、「贏 8 比 1 也沒有加分」）和 Rosenof 論文的發現 —— 他的 H₀ 演算法 "implicitly learns to punt a subset of categories"，不是被人教的。

## 三、標準差要用 G-score 的分母，不是 Z-score 的

這是論文最實用的一個結論，而且很容易漏掉。

**Z-score 的分母只有球員間標準差 σ**。
**G-score 的分母是 √(σ² + κ·τ²)**，多了**週間（期間間）標準差 τ**。

完整公式（Rosenof, arXiv:2307.02188 Table 5c）：

```
計數型（PTS, REB, AST, STL, BLK, 3PM）：
    G = ( μM(q) − μM ) / √( σM² + κ·τM² )

失誤（越低越好，分子反向）：
    G = ( μM − μM(q) ) / √( σM² + κ·τM² )

命中率型（FG%, FT%）：
    G = [ (a_q / μA) × ( μR(q) − μR ) ] / √( σR² + κ·τR² )
```

| 符號 | 意義 |
|---|---|
| μM(q) | 球員 q 每個計分期間的平均值 |
| μM | 所有在籍球員 μM(q) 的平均 |
| σM | **球員之間**的標準差（Z-score 只用這個） |
| τM(q) | 球員 q **自己期間與期間之間**的標準差 |
| τM | 所有球員 τM(q) 的均方根 |
| κ | 2N/(2N−1)，N = 每隊每期間場數；12–13 人名單約 **1.04** |
| a_q / μA | 該球員的出手量 ÷ 平均出手量（命中率類別的量級加權） |
| μR(q), μR | 出手量加權的綜合命中率 |

論文原文：

> "Z-scores are equivalent to G-scores with |W|=1, removing all period-to-period variance"

**實務影響有多大**：論文 Table 8（2022-23 資料）顯示 **抄截的 Z 分母是 1.00，G 分母是 2.28** —— 也就是說用 Z-score 會把抄截的重要性**高估一倍以上**。阻攻同理。這兩個剛好是最常被串流追逐的類別。

**模擬實證**（12 隊、13 人名單、每個選秀位 1,000 季）：

| 設定 | Each Category 勝率 | Most Categories 勝率 |
|---|---|---|
| G-score 一隊 vs Z-score 十一隊 | **21.4%** | **32.5%** |
| Z-score 一隊 vs G-score 十一隊 | 0.5% | 0.4% |
| 隨機基準 | 8.33% | 8.33% |

這是模擬不是實戰，且模型有簡化，但差距大到難以用噪音解釋。

**所以：σ_lg[c] 在步驟 5 要用 √(σ² + κτ²) 算，不是只用 σ。** 這一行改動大概就值整個引擎其他部分的一半。

## 四、命中率類別的陷阱

FG% 和 FT% **不能直接比較百分比**，必須用出手量加權。

```python
# 錯的
value_fg = player.fg_pct - league_avg_fg_pct

# 對的
value_fg = (player.fga / league_avg_fga) * (player.fg_pct - league_avg_fg_pct)
```

直覺：一個 FT% 95% 但每場只罰 0.5 球的人，對你的 FT% 幾乎沒影響；一個 FT% 65% 但每場罰 9 球的人會把你整週的 FT% 拖垮。後者的「傷害」是前者「幫助」的十幾倍。

你的聯盟是 13 類，可能包含 FGM / FTM / 3P% / A-TO / OREB / DREB / DD 之類。**開工第一件事是把 `/league/{lk}/settings` 的 `stat_categories` 抓下來存檔**，每一類都要確認方向（越高越好 or 越低越好）和是否為比率型。不要假設是標準 9 類。

## 五、每週的撿人額度要怎麼分配

你有每週 8 次撿人額度。這是個預算分配問題，不是貪心問題。

```
週一（本週第一天）：
  用 2~3 次，搶「本週剩餘場次最多」的人
  理由：剩 4 場的人提供的總量是剩 1 場的人的 4 倍，而額度是固定的
  → 週初的一次撿人比週末的一次值錢得多

週二~週五：
  每天最多 1 次，只在「swing 類別的勝率能提升 >8 個百分點」時才動
  理由：留彈性應對傷病

最後 2 天：
  保留 1~2 次應急（有人突然 Out）
  如果某個 swing 類別只差一點點，這時候可以 all-in
```

**推播裡要顯示「這次撿人的勝率提升」**，讓你自己決定值不值得花掉一次額度。像這樣：

```
建議撿人：Keon Ellis (SAC)  —  但這會用掉本週第 4 次額度（剩 5 次）
  本週剩 3 場
  影響：STL 勝率 31% → 58%  (+27pp)   ← 值得
         3PM 勝率 44% → 51%  (+7pp)
         整體預期贏得類別數 6.2 → 6.9
放掉建議：Moussa Diabaté (CHA, DTD)
  本週剩 2 場但狀態不明；他主要貢獻 REB/FG%，兩者都已 lock
```

## 六、要不要用 AI？

你說「能不用 AI 就不用，但要有效益」。我的結論是 **v1 完全不用 AI**，理由不是省錢，是**可靠性**。

### 不該用 AI 的部分（佔 95%）

賽程、傷病狀態、類別累積值、期望值、標準差、勝率、排序 —— 這些全部是**確定性計算**。交給 LLM 的話：

- 慢（每天多等幾十秒）
- 貴（每天都跑）
- **會算錯**（LLM 做多步算術本來就不可靠）
- **不可重現**（同樣輸入可能不同輸出，你沒辦法事後檢討「當時為什麼推薦他」）

而且「為什麼」的解釋**用模板反而比 LLM 更可信**，因為模板裡的每個數字都是算出來的：

```python
f"撿 {name}：你本週 {cat} 落後 {gap:.1f}，他剩 {games} 場、"
f"場均 {per_game:.1f} {cat}，可把 {cat} 勝率從 {p_before:.0%} 拉到 {p_after:.0%}"
```

這段話沒有任何幻覺空間。LLM 寫同樣的話，你還得擔心它把數字抄錯。

### 真的值得用 LLM 的兩個地方

| 位置 | 為什麼規則寫不出來 | 成本 |
|---|---|---|
| **傷病新聞的自由文字理解**。ESPN 的 `shortComment` / `longComment` 裡藏著「預計缺席 2–3 週」、「Smith 會接替先發」、「教練說會限制上場時間」這類訊息 | 這是自然語言理解。要用規則抽出「誰會吃到球權」幾乎不可能，而這恰好是串流最大的 alpha 來源 | 一天一次、只處理有變動的那幾筆，極便宜 |
| **異常情境的總結**。例如同隊 3 人同時 Out、或你 5 個先發今天都沒比賽這種罕見狀況 | 規則無法窮舉 | 很少觸發 |

### 建議的落地順序

```
v1  純計算 + 模板          → 先跑兩週，看推薦準不準
v2  加一個 LLM 步驟處理傷病新聞文字 → 輸出結構化 JSON（預計缺席場次、受益球員）
    結構化後的結果再餵回確定性引擎 ← 關鍵：LLM 只做翻譯，不做決策
v3  如果 v1 的自製投影誤差太大，花 $2.50/月訂 Hashtag 的 STREAM7/14/30
```

**原則：讓 LLM 做「文字 → 結構」，絕不讓它做「結構 → 決策」。**

## 七、驗證：怎麼知道引擎有沒有用

每天把推薦和實際結果都存檔，一兩週後回頭算：

1. **投影誤差**：預測的每場類別值 vs 實際。分類別看 MAE，找出哪一類最不準
2. **勝率校準**：所有「預測 60% 會贏」的類別，實際是不是贏了大約 60%？（可靠度圖）
3. **決策價值**：如果我當天聽了推薦 vs 如果我只用 Start Active Players，本週類別數差幾個？
   → 這是唯一真正重要的指標。**如果這個數字接近 0，就該停掉這個專案，直接用內建功能。**

第 3 點要誠實做。有可能算出來發現「每週只多贏 0.2 類」，那就不值得每天花時間。先驗證再投入。
