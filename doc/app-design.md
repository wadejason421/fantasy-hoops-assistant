# App 設計：即時 Box Score 與 Play-by-Play

> 這份是**可行性評估 + UI 設計**，還沒有實作。

## 一、結論：可行，而且不需要伺服器

但架構不是自由選的 —— 有一個實測出來的限制把選項砍掉一半。

| 問題 | 答案 |
|---|---|
| 做得出來嗎？ | **可以**，純前端網頁，零伺服器、零月費 |
| 即時嗎？ | **可以**，比賽進行中約 10~20 秒延遲 |
| 能看 box score 嗎？ | 可以，14 項傳統數據 + 先發/上場時間 |
| 能看 play-by-play 嗎？ | 可以，完整逐筆 + 當下比分 |
| 有投籃圖嗎？ | **即時沒有，賽後有**（原因見第三節） |
| 要花錢嗎？ | 不用。GitHub Pages 免費代管 |

## 二、決定架構的那條限制：CORS

瀏覽器只能向「允許跨網域」的伺服器發請求。實測（從 `https://example.com` 發 `fetch`）：

| 來源 | 跨網域可用？ |
|---|---|
| `cdn.nba.com`（NBA 官方 liveData） | ❌ **被擋** — `Failed to fetch` |
| `site.api.espn.com`（ESPN 賽程／box score／plays） | ✅ 200 |
| `sports.core.api.espn.com`（ESPN 詳細 plays） | ✅ 200，903 KB |
| `raw.githubusercontent.com`（我們自己 repo 的資料） | ✅ 200 |

**NBA 官方那條路在瀏覽器裡死得很徹底。** 注意這跟先前的 TLS 指紋問題是**兩件不同的事**：

| 障礙 | 誰會中 | 怎麼解 |
|---|---|---|
| TLS 指紋 | curl、Python、任何非瀏覽器客戶端 | `curl_cffi` 偽裝（已解決） |
| **CORS** | **瀏覽器**（瀏覽器的指紋本來就對） | **解不了** — 這是瀏覽器強制的，伺服器不給就是不給 |

瀏覽器打 `cdn.nba.com` 的諷刺之處：它的 TLS 指紋完美（它就是 Chrome），卻被 CORS 擋下。
而 `curl_cffi` 沒有 CORS 問題（CORS 只存在於瀏覽器），卻要偽裝指紋。兩邊剛好互補。

> 唯一的繞法是架一個自己的代理伺服器（它用 `curl_cffi` 抓，再加上 CORS header 轉給前端）。
> 那要錢、要維運，而且回到「電腦要常開」的老問題。評估下來不值得 —— 見第三節的取捨。

## 三、建議架構：兩個資料源各司其職

```
┌─────────────────────────────────────────────────┐
│  瀏覽器裡的前端（GitHub Pages 免費代管）          │
│                                                  │
│   比賽進行中 ──► ESPN API（直接 fetch，10~20s 輪詢）│
│                  比分、box score、play-by-play     │
│                                                  │
│   賽後分析  ──► raw.githubusercontent.com        │
│                  我們 repo 裡的官方資料            │
│                  含投籃 x/y 座標、descriptor       │
└─────────────────────────────────────────────────┘
          ▲
          │ 每天台北 16:23
    GitHub Actions（curl_cffi 抓 NBA 官方）
```

**即時用 ESPN，賽後用官方。** 理由：

- 即時的場景是「現在比分多少、誰在得分」—— ESPN 的資料完全夠
- 投籃座標的價值在**賽後分析**（投籃分佈圖、熱區），不是比賽當下
- 官方資料反正每天都會進 repo，前端直接讀 raw URL 就好，不用另外架服務

### 兩邊的資料能力對照

| | ESPN（即時） | NBA 官方（賽後，從 repo） |
|---|---|---|
| 球員 box score | 14 項（MIN/PTS/FG/3PT/FT/REB/AST/TO/STL/BLK/OREB/DREB/PF/+-） | **33 項**（多 2PT、快攻得分、禁區得分、被封阻、製造犯規、plus/minus 分開） |
| play-by-play 筆數 | 488 | **590**（多換人、暫停等） |
| 投籃座標 | 粗略整數，非投籃事件是垃圾值 | **精確 x/y + 距離 + 左右側** |
| 投籃方式 | 只有文字描述 | **`descriptor` 欄位**（step back / driving / fadeaway） |
| 助攻者 | 在文字裡 | **獨立欄位** `assistPersonId` |
| 進階數據 | ❌（`VORP` 回 0.0） | 自己算（TS%/eFG% 與官方一致） |
| 單節比分 | ✅ | ✅ |
| 延遲 | 約 10~20 秒 | 隔天 |

### 即時更新的行為細節

這幾點不做好，體驗就是垃圾：

| 問題 | 做法 |
|---|---|
| 輪詢浪費 | 只在**分頁可見**時輪詢（`document.visibilityState`）。切走就停 |
| 比賽結束還在打 | `status.type.state !== 'in'` 就停止輪詢，改成手動重整 |
| 整頁重繪導致捲動跳掉 | 只更新變動的節點，play-by-play 用 key diff 往上插入新項目 |
| 使用者不知道有沒有在更新 | 標題列放「⟳ 15s」倒數，更新瞬間轉一圈 |
| 比分變化沒感覺 | 數字變化時閃一下底色（200ms），不要用動畫捲動（晃眼） |
| 網路斷掉 | 連續失敗 3 次顯示「連線中斷，重試中」，退避到 60 秒 |
| 看球多在晚上 | **預設深色**，跟隨系統 |

### 不做的東西

- 不做登入、不做帳號 —— 沒有需要保護的資料
- 不做推播 —— PWA 推播在 iOS 限制多，不值得
- 不做即時投籃圖 —— ESPN 座標太粗，官方的隔天才有。賽後再看

## 五、技術選型

| 項目 | 選擇 | 理由 |
|---|---|---|
| 形式 | **網頁（PWA）** | iOS/Android/桌機一份程式。原生 app 用系統 HTTP stack，反而會被 NBA 的指紋檢查擋 |
| 代管 | **GitHub Pages** | 免費，跟資料在同一個 repo，推上去就部署 |
| 框架 | 不用框架或 Preact | 畫面簡單，兩三千行以內。避免為了一個看球頁面裝一整套工具鏈 |
| 狀態 | 輪詢 + 記憶體 | 不需要狀態管理函式庫 |
| 離線 | Service Worker 快取靜態檔 | 可以「加到主畫面」當 app 用 |

## 六、未知數與風險

| 風險 | 程度 | 說明 |
|---|---|---|
| **ESPN 即時行為未驗證** | 🔴 高 | 所有測試都在賽後做的。ESPN 比賽中更新多快、會不會有快取延遲，**沒測過**。必須在有比賽時實測 |
| ESPN 改介面 | 🟡 中 | 未公開介面，沒有保證。要做 schema 檢查與降級 |
| ESPN 擋 CORS | 🟡 中 | 現在開放，哪天關掉就整個前端失效。屆時只能架代理 |
| GitHub Pages 流量 | 🟢 低 | 軟上限 100 GB/月，自己用遠遠用不到 |
| NBA 官方資料斷更 | 🟢 低 | Actions 失敗會寄信，而且前端只在賽後才用它 |

**第一個風險是真正的門檻。** 建議第一步不是寫 UI，是在有比賽時跑一支 30 行的腳本，
每 10 秒打一次 ESPN，確認 `plays` 會變長、比分會跳。那個結果決定要不要往下做。

## 七、分階段

| 階段 | 內容 | 產出 |
|---|---|---|
| **0** | 驗證 ESPN 即時性（有比賽時跑輪詢腳本） | 一份 log，證明資料會動 |
| 1 | 今日比賽列表 + 單場總覽，ESPN 資料 | 能看比分的網頁 |
| 2 | Box Score 分頁 + 展開細節 | 可用的看球工具 |
| 3 | 逐球紀錄分頁 + 篩選 | 完整即時體驗 |
| 4 | 接上 repo 的官方資料：賽後投籃圖、33 欄完整 box score | 賽後分析 |

階段 0 做不過，後面全部不用做 —— 所以先做它。
